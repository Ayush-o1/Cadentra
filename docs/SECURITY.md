# Security

What was considered, what controls exist and where they are tested, and what is not done. Sources are the OWASP Top Ten and the OWASP Password Storage and Session Management guidance; the Phase 0 research notes which of those figures were seen only in secondary summaries ([RESEARCH.md](RESEARCH.md)). This is a self-review, not an external audit.

## Threats and controls

| **Broken access control, IDOR**               | The workspace comes from the session, never the request. Every query is scoped by it. Foreign IDs return 404. ## Auditing

Important actions write to `activity_log` (workspace created and updated, contacts created, edited, deleted and imported, lists, campaign lifecycle, suppressions, unsubscribes). The dashboard shows the latest entries.

## Verification performed for this release

- **Automated accessibility scan** (axe, WCAG 2.1 A and AA) on every page and the contact dialog. It found two real problems (faint-text contrast, account button name), both fixed.
- **`npm audit --omit=dev`** (what ships): 0 vulnerabilities. CI fails on high severity in production dependencies.
- **`npm audit`** (including development tools): 7 moderate findings, all one advisory, a denial of service in `minimatch` glob matching reached through `typescript-eslint`. It affects only the local lint tooling, which never processes untrusted patterns, and is not in the production image. npm's suggested fix is a downgrade to an older `typescript-eslint`, so it was not applied. Revisit when `typescript-eslint` ships a patched `minimatch`.
- **Secret scan** of every tracked file and of the full Git history for API-key, webhook-secret, private-key and token patterns: no matches. `.env` is ignored and was never committed.
- **Headers and behaviour** checked against the production container with `scripts/smoke-test.mjs`.

## Known gaps

These are real and are not hidden by the controls above.

- **Email confirmation is optional.** The link is sent at sign-up and can be required before launching (`REQUIRE_VERIFIED_EMAIL=true`), but is not required by default, because without a verified sending domain the provider cannot deliver it to anyone but the account owner. Until it is enforced, anyone can register with any address. Sending still requires a sender identity on a domain verified with the provider, a consent basis per contact, and the daily limit.
- **No multi-factor authentication, no account lockout beyond rate limiting, no way to change the account email.** Password reset exists.
- **Rate limits are in memory.** They reset on restart and are per instance. Behind a proxy `TRUST_PROXY` must be set to the number of proxies so the client IP is correct (the deployment guide has a check).
- **Single owner per workspace.** There are no invitations; the `member` role exists in the schema and is enforced where it matters (workspace settings) but cannot yet be assigned through the UI.
- **No per-workspace provider keys.** One provider key lives in the server environment.
- **Erasure is incomplete for audit data.** Deleting a contact removes its recipient and message rows, but the activity log keeps the event type (not the address, except unsubscribes and suppressions, which record the address by design).
- **CHECK constraints may be inactive on TiDB.** On MySQL they are enforced; TiDB documents them as off by default. The application validates the same rules. See [TIDB_COMPATIBILITY.md](TIDB_COMPATIBILITY.md).
- **Self-audited.** No penetration test or external review has been done.
